# Working with this repo

## How Maxim wants to work
This is a learning project as much as a build. Default to **explaining before
implementing**, not silently producing finished code:

- Before writing code for a task, briefly explain the approach and why, and
  wait for a go-ahead if the approach involves a real choice (not for trivial
  things like a typo fix).
- Implement in small, reviewable chunks rather than one large diff — one
  feature or one file at a time, not a whole task tier at once.
- After each chunk, briefly explain what the code does, not just that it's
  done — assume the goal is understanding, not just a working app.
- Don't auto-advance to the next task after finishing one. Stop, let Maxim
  review/run it, and wait to be told to continue.
- It's fine to be concise — explanations should teach, not lecture. Skip
  restating things already covered earlier in the same session.

## Task tracking
`TASKS.md` at the repo root is the backlog, grouped by priority (P0 highest).
Work top to bottom within a tier unless told otherwise. Check items off
(`[ ]` → `[x]`) as they're completed, as part of the commit for that task,
not in a separate step.

## Project context
Side project with a friend (she does design, Maxim does backend/technical).
Working name: "Pion". Goal: chess.com-style app to play chess live with a
friend on another device; later a mobile app; later RFID/NFC board hardware
integration (see TASKS.md P3).

## Stack
- Monorepo: pnpm workspaces + Turborepo
- `apps/web` — Next.js (App Router), React, TypeScript, Tailwind
- `apps/server` — Fastify + Socket.io (standalone, not serverless — needs
  persistent WebSocket connections)
- `packages/shared` — Zod schemas shared across web/server/future mobile app
- `packages/db` — Prisma 7 ORM + PostgreSQL (local), driver-adapter based
  client (`@prisma/adapter-pg`)
- Chess logic: chess.js (rules/validation) + react-chessboard (UI) — not yet
  installed
- Future analysis feature: self-hosted `stockfish.wasm`, local CPU

## Known gotchas (don't rediscover these)
- Always run `pnpm` commands from the repo root using `pnpm --filter <name>
  <cmd>`, never `cd` into a package and run pnpm directly — it has broken
  workspace resolution twice before (stray nested `pnpm-workspace.yaml` /
  `pnpm-lock.yaml` appearing inside `apps/web`).
- Prisma 7: connection URL lives in `prisma.config.ts` only (`defineConfig`
  from `prisma/config`), never in `schema.prisma`'s `datasource` block.
  `PrismaClient` requires an explicit driver adapter.
- Each package needing `DATABASE_URL` needs its own `.env` (Prisma commands
  run from `packages/db`, the server runs from `apps/server`) — see the
  `.env.example` file in each for the expected shape.
- `packages/db/.agents` `.claude` `.cursor` `.devin` folders are
  auto-generated by a Prisma postinstall hook — gitignored, don't hand-edit.
